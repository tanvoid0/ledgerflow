- **Chat tab** — [Chat.kt](src/main/kotlin/io/ledgerflow/trainer/ui/Chat.kt) `ChatPanel`, new "Chat" tab. Backend dropdown: Ollama (`Reviewers.ollamaChat`, `/api/chat`, turn history kept client-side since Ollama has no session) or agent-platform's Coder agent (`Reviewers.agentChat`, `/api/v1/coder/chat/send`) — the actual tool-loop backend: it runs `read_file`/`write_file`/`list_dir`/`search`/`repo_map`/`run_command` in a server-side loop (`run_agent_turn`) per turn, so this is one HTTP call per turn, not per tool step. Turn-based, not streamed — a reply lands whole.
  - **Session history** — saved to SQLite after every completed turn, so a conversation survives closing the tool window and the IDE. Its own database (`ide-trainer/chats.db`, one per *project*) rather than an experiment's `trainer.db`: a conversation is not about one curriculum, and storing it per-experiment would hide it the moment you switched paths. Tables `chat` + `chat_turn` live in `TrainerDb.migrate` alongside the progress ones, so an experiment db just never writes rows into them. History button (clock icon, top right) lists past conversations newest-first; picking one restores the transcript, the turn list and the agent `thread_id`. "New Chat" now starts a new session rather than discarding the old one. Turns are recorded for **both** backends — Agent Platform conversations otherwise lived only in the server-side thread and would come back from the list empty.
  - **`@` file context.** Typing `@` opens a fuzzy picker over the project's files (IntelliJ's own `MinusculeMatcher` via `NameUtil.buildMatcher`, file list built once per panel off `ProjectFileIndex.iterateContent`). Picking one inserts `@relative/path`; at send time each mention is resolved through `Ide.resolve` and its content (capped at 4k chars) is appended to the *outgoing* prompt only. Ollama history keeps the raw `@path` text, not the expansion — replaying the dump every turn would balloon the prompt turn over turn. Plain text, not chips: the input is a `JBTextField`, and atomic chips would mean swapping it for an `EditorTextField` + inlays. The popup is created with `setRequestFocus(false)` deliberately — focused, it swallows everything typed after the first character into its own speed-search and filter-as-you-type dies; keyboard handling lives on the input field instead (Enter/Tab take the top match, Escape dismisses, and consuming the event is what stops a completing Enter from also sending the turn).
  - **Mode dropdown** (replaces the old "Allow shell commands" checkbox): Chat / Plan / Code (manual) / Code (auto). Each maps to a preamble plus the `allow_commands` + `auto_approve_commands` flags on `/send`. Plan mode additionally writes the reply to `<slug>.plan.md` at the project root via `Ide.createFile` (never overwrites; slug derived from the prompt). No allowlist and no per-call "run once / always allow" prompt — see Blocked below: the tool loop is server-side, so there is nothing here to intercept and such a control would gate nothing.

- **Local tool loop** — [AgentLoop.kt](src/main/kotlin/io/tanvoid0/codecraft/AgentLoop.kt) + [AgentTools.kt](src/main/kotlin/io/tanvoid0/codecraft/AgentTools.kt). The Ollama backend now runs its own tool loop in-process (`read_file`/`list_dir`/`search`/`run_command`, via Ollama's function-calling `tools` param and `Reviewers.ollamaRound`), instead of being a text box that could only see hand-`@`-mentioned files. Tools are built on primitives that already existed: reads go through `Ide.resolve`, commands through the new `Ide.runCapturing` (extracted from `Ide.verify`, which had the ProcessBuilder/drain/timeout logic but threw the output away — `runInTerminal` shows output to a human but can never read it back, so it is useless to an agent).
  - **This is what makes permissions real.** Every gated call passes `AgentLoop.Watcher.approve` before running, so Code (manual) prompts run-once / always-allow / deny; "always" is session-only and deliberately not persisted. That closes the gap recorded under Blocked below — but only for Ollama. Agent Platform still loops server-side and still cannot be gated from here.
  - Editing is deliberately **not** a tool. A model rewriting files unattended is the one thing this plugin has always refused; `Ide.patchFile` puts a diff in front of the learner instead.
  - `AgentLoop` takes its tool access as three functions rather than an `AgentTools`, so the loop's control flow is testable without a `Project` — [AgentLoopTest.kt](src/test/kotlin/io/tanvoid0/codecraft/AgentLoopTest.kt) drives it with a scripted model and covers refusal, ungated reads, runaway-loop capping, cancellation, and tool results reaching the next round.
  - Stop button (visible only mid-turn) sets a flag the loop checks between rounds and between calls. Tool activity is echoed into the transcript as it happens, elided past 6 lines — an agent working in silence is indistinguishable from a hung one.

- **Streaming replies** — `Reviewers.ollamaStream` reads `/api/chat` with `stream: true` as NDJSON and calls back per fragment, so Chat/Plan answers appear as they generate. Reads the body as an `InputStream`, not a String, because that is what makes Stop real: the abort flag is polled between lines and closing the stream ends generation mid-reply, where before Stop could only take effect between tool rounds. Whatever arrived before the stop is kept. Token counts still come off the final line, so the usage readout did not regress. Auto-scroll only follows when the view is already at the bottom — otherwise reading back through earlier output yanks you down on every token. [OllamaStreamTest.kt](src/test/kotlin/io/tanvoid0/codecraft/OllamaStreamTest.kt) covers it against a JDK stub server: **whitespace-only fragments surviving** (the codebase's own `str()` helper drops blank strings — using it here would have silently run every word together), per-token delivery, malformed lines being skipped rather than fatal, abort keeping partial output, and usage parsing.
- **Tool-window icon test un-pinned.** `ToolWindowRegistrationTest` asserted `icon == "AllIcons.Actions.Learn"` while `plugin.xml` had long since moved to the bundled `/pluginIcon.svg`, so the suite was permanently red over a non-defect. It now asserts what the test's own doc says it guards — that an icon is set, and that a bundled path actually resolves on the classpath — instead of pinning a literal that every rebrand breaks.

- **Edit tools (ADR-002 item 1)** — `edit_file` (exact-match replace) and `write_file` in `AgentTools`. `edit_file` refuses unless `old_string` occurs **exactly once**: zero means the model is editing a file it half-remembers, more than one means it never said which occurrence it meant, and picking for it is how an agent silently corrupts a file. Code (manual) shows the change in the IDE's own diff viewer (`Ide.confirmEdit` → `PatchPreview`) and applies nothing until Apply is clicked; Code (auto) skips the dialog but still writes through one undoable `WriteCommandAction` per file (`Ide.applyEdit`), so Ctrl+Z and git stay the net. Chat/Plan are handed no tools at all, so the mode is enforced by absence rather than by asking nicely.
  - Edits are **not** routed through `AgentLoop.Watcher.approve` — that gate shows the command dialog, and an edit is approved by reading its diff, which only `AgentTools` can compute. Sending edits through both would prompt twice for one change. The `AgentTools` class doc had claimed a single shared gate; corrected.
  - `countMatches` is top-level and tested ([EditMatchTest.kt](src/test/kotlin/io/tanvoid0/codecraft/EditMatchTest.kt)) because it is the whole safety property, and `split().size - 1` gets overlapping needles ("aa" in "aaa") wrong.

- **Content search (ADR-002 item 2)** — `grep` in `AgentTools`, alongside the existing `search`. The two are not the same tool and the schema says so: `search` matches file *paths*, `grep` matches file *contents* and answers `path:line: text`, which is what an agent fixing a bug actually needs. Walks `ProjectFileIndex` like `search` does — no new dependency, no index to build. Binaries and files over 500KB are skipped rather than scanned (a hit inside a jar or a megabyte of minified JS is never the answer), and the 100-hit cap is announced in the output, on the same rule as `read_file`'s truncation: a capped list must never read as a complete one.

- **Editor context (ADR-002 item 3)** — `Ide.editorContext` reads the open file, the caret line, and the IDE's own diagnostics for that file; `editorPreamble` (pure, in Chat.kt) turns them into the two lines that go in front of the question. The diagnostics are the part that earns its place: without them the model asks for a build to learn what the editor already had underlined. Warnings and above only — weak-warning noise would spend the budget on "unused import" in a file the question is not about. Read through `DaemonCodeAnalyzerImpl.getHighlights`, which returns nothing until the analyser has passed over the file; that is a normal state, so the whole thing is best-effort and a project with no editor open simply sends less. Prepended to the outgoing turn only, never added to `turns` — replayed later it would tell the model the learner is still looking at a file they closed ten turns ago.

- **Rules file, context budget, deeper Code loop (ADR-002 items 5–6)** — all in [Chat.kt](src/main/kotlin/io/tanvoid0/codecraft/ui/Chat.kt), pure functions so they are testable without a project ([ChatContextTest.kt](src/test/kotlin/io/tanvoid0/codecraft/ChatContextTest.kt)).
  - `rulesPreamble` reads the first of `ide-trainer/RULES.md`, `RULES.md`, `CLAUDE.md` that has content into the system turn, capped at 4k and re-read every turn so editing the file needs no restart. A blank file falls *through* to the next candidate rather than winning with nothing. This repo already keeps its conventions in `CLAUDE.md` — the rules a human agent is handed are the ones the local model should get too.
  - `trimHistory` caps replayed history at 24k chars, dropping oldest-first. Without it the prompt grows every turn until the model's own context silently truncates it — which drops the same turns, just without anyone knowing. Whole turns only (a user message whose answer was cut is worse than neither), and the newest turn survives any budget: sending no question at all is worse than sending a long one.
  - `maxRounds` for Code modes is 20, not the loop's default 8. An edit-build-fix cycle spends a round per step, and running out mid-repair reads as a wrong answer rather than a stopped one.
  - Transcript now uses the editor's own font, so fenced code and tool output line up instead of drifting in a proportional face. One font for the whole transcript, not per-block — a real Markdown renderer needs an editor pane, which stays the upgrade path.

## Blocked

- **~~Coder tool-call approval not wired~~ — done 2026-08-30, both sides.** `Reviewers.agentChat` returns an `AgentTurn` (`text`, `threadId`, `pending`) instead of a pair, and a parked turn is answered by `Reviewers.agentApprove` → `POST /api/v1/coder/chat/approve/send`; `ChatPanel.resolvePending` loops that until the turn answers, stops, or hits the same round ceiling the local loop has. The prompt is the *same* gate the Ollama loop uses (`approveCommand`) with the same session-only allowlist, so "Code (manual)" no longer means two different things depending on the backend, and `auto_approve_commands` stops being the only way to get work out of the Coder agent. A refusal is posted rather than dropped — the server records it as the tool result and tells the model, which is what stops it retrying the same command forever. A `pending_call` for a tool carrying no `command` (`write_file`) is still asked about, by name. [AgentApproveTest.kt](src/test/kotlin/io/tanvoid0/codecraft/AgentApproveTest.kt) covers the parked/answered/content-block shapes and both verdicts against a stub server. Server half below.

- ~~**Coder tool-call approval not wired** (original note).~~ agent-platform now serves `POST /api/v1/coder/chat/approve/send`, a plain-JSON twin of the SSE `/approve` (its `run_approval` is shared by both, so the two cannot drift). That removes the reason this was blocked: `/send` already returns `pending_call`, and the answer to it no longer needs an SSE client. **What remains is here, not there** — `Reviewers.agentChat` currently reports a `pending_call` into the transcript and stops; it needs to surface the same run-once / always-allow / deny dialog the Ollama path uses (`ChatPanel.askToRun`) and POST the verdict to `approve/send`. Once that lands, Code (manual) means the same thing on both backends and `auto_approve_commands` stops being the only way to get work out of the Coder agent. Original note follows.

- **Coder tool-call approval not wired.** When agent-platform's Coder agent hits something it gates further internally (its `pending_call` — seen on `run_command`; unclear yet whether `write_file` is also gated), this client surfaces that fact in the transcript instead of resolving it — the real resolve path (`/api/v1/coder/chat/approve`) is SSE, not the plain JSON `/send` this panel uses. Untested end-to-end (agent-platform team-template bug above blocked getting the server past auth into an actual chat call this session). If `write_file` turns out to be gated too, most real edits will hit this path — worth testing before relying on the chat to edit files. This is also what blocks a real permission UI: the chat's "Code (auto)" mode sets `auto_approve_commands` and lets the server approve itself, because with no SSE approve client the only alternative is the dead end above. A command allowlist, or a "run once / always allow / deny" dialog, needs this route wired first — until then it would be a control that controls nothing.
